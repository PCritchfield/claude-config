# claude-config

Version-controlled backup of the hand-maintained files that live in `~/.claude/`. This repository exists so those files are not lost when a machine changes, and so there is a clear record of what changed and why.

---

## What lives here

```
claude/.claude/
├── settings.json       # Claude Code settings: model, permissions, env vars, hooks, spinners
├── rules/              # Path-scoped rule files (loaded contextually, not always)
│   └── obsidian.md            # Session summaries, vault search via MCP
├── agents/             # Empty; the agent layer is the crew plugin (see below)
├── hooks/              # Lifecycle hooks
│   ├── session-start-context.sh  # Loads prior Obsidian session as context
│   └── precompact-checkpoint.sh  # Saves checkpoint before context compaction
├── commands/           # SDD commands (generated by slash-man, gitignored)
└── skills/             # Custom skills (community skills installed separately, gitignored)
    ├── obsidian-digest/
    └── obsidian-summary/
```

The files are stored under `claude/.claude/` rather than directly at the repo root so the repository can hold other things (this README, for instance) without polluting the Claude config directory.

## Installing

Setup has three steps. Each is independent — run what you need.

### Step 1: Stow symlinks

```bash
./install.sh
```

Creates symlinks from `~/.claude/` pointing into the repo using [GNU Stow](https://www.gnu.org/software/stow/). Requires `stow` (`brew install stow`). The script automatically backs up any pre-existing real files before replacing them with symlinks.

### Step 2: Community skills

```bash
./install_skills.sh
```

Installs 27 community skills from the `skills.txt` manifest via `npx skills add`. These are domain skills (security, architecture, database, IaC, etc.).

**Prerequisite:** Install the [obra/superpowers](https://github.com/nicholasgriffintn/superpowers) plugin first — it provides 14 core skills (systematic-debugging, test-driven-development, etc.) that overlap with the manifest. Install via Claude Code: `/plugins` → search "superpowers" → install.

### Step 3: SDD commands

```bash
uvx --from git+https://github.com/liatrio-labs/slash-command-manager \
  slash-man generate \
  --github-repo liatrio-labs/spec-driven-workflow \
  --github-branch main \
  --github-path prompts/
```

Generates the `/SDD-1` through `/SDD-4` slash commands from the [spec-driven-workflow](https://github.com/liatrio-labs/spec-driven-workflow) repository.

### Step 4: Obsidian MCP Server (optional)

If you use Obsidian for session notes:

1. Install the [Local REST API plugin](https://github.com/coddingtonbear/obsidian-local-rest-api) in Obsidian (Community Plugins → Browse → "Local REST API")
2. Enable it and copy the API key from its settings
3. Add the MCP server:
   ```bash
   claude mcp add obsidian --scope user -- npx -y obsidian-mcp-server
   ```
4. Set the environment variables in `~/.claude.json`:
   ```json
   "obsidian": {
     "env": {
       "OBSIDIAN_API_KEY": "<your-key>",
       "OBSIDIAN_BASE_URL": "https://127.0.0.1:27124",
       "OBSIDIAN_VERIFY_SSL": "false"
     }
   }
   ```

### settings.json is synced, not stowed

Claude Code's tools replace a symlinked `settings.json` with a regular file the
first time they save it, so it is kept in step by git instead: captured into the
repo at every session end, applied from the repo after every `git pull`. On a
fresh machine, `install.sh` seeds it from the repo. See
[CONTRIBUTING.md](CONTRIBUTING.md#read-this-first-the-repo-is-your-live-config).

Check it for local absolute paths and update them on a new machine:

- `OBSIDIAN_VAULT` — set to the vault location on this machine

## rules/

`.claude/rules/` holds one file, **obsidian.md** — session summary rules and vault search patterns via MCP. Rules files load contextually.

## Agents: the crew plugin

The agent layer is the `crew` Claude Code plugin ([PCritchfield/claude-crew](https://github.com/PCritchfield/claude-crew), currently a private repo), not files in this repo. It provides:

- The Rincewind persona and routing context, loaded by a SessionStart hook
- Read-only guardians (`crew:security`, `crew:architecture`, `crew:data`, `crew:infra`) that can return BLOCK
- Builders (`crew:coder`, `crew:frontend`, `crew:iac`, `crew:db`, `crew:delivery`, `crew:devenv`, `crew:docs`)
- The `crew:review` and `crew:polish` skills

Superpowers drives the process. Install:

```
/plugin marketplace add PCritchfield/claude-crew
```

then install `crew@crew` from that marketplace.

## Hooks

Three lifecycle hooks in `settings.json`:

| Hook | Event | Purpose |
|------|-------|---------|
| `session-start-context.sh` | SessionStart | Loads the most recent Obsidian session note for the current project/branch as `additionalContext`. Ends cold starts. |
| `precompact-checkpoint.sh` | PreCompact | Saves a lightweight checkpoint marker to the Obsidian vault before context compression. Non-blocking, best-effort. |
| PostToolUse (inline) | Write/Edit | Auto-formats with ruff (Python) and prettier (JS/TS/CSS/JSON) on changed files. |

## skills/

Two hand-maintained skills. Community skills (33 from various repos) are installed separately via `install_skills.sh` and gitignored — they create symlinks into `~/.agents/skills/` and are not tracked in this repo.

### obsidian-summary

Saves a structured session summary to an Obsidian vault. Supports four note types: `session`, `document`, `decision`, and `investigation`. Produces Obsidian-flavoured markdown with YAML frontmatter, wikilinks, and Dataview-compatible properties.

The vault path is read from the `OBSIDIAN_VAULT` environment variable set in `settings.json`. Run it before context compaction, which loses decisions and findings that are worth keeping.

Files:
- `SKILL.md` — full skill definition
- `write-to-vault.sh` — writes the generated note to the correct vault path

### obsidian-digest

Synthesises multiple session notes into a structured digest and optional Marp slide deck. Scopes by project, feature, topic, or date range. Output tone and depth adapts to the intended audience (personal, team, leadership, or client-facing) — leadership and client-facing strips agent findings and commit refs; team and personal keeps full technical depth.

Uses `obsidian-summary`'s `write-to-vault.sh` for writing to the vault. Marp slide generation is optional and checks for CLI availability before attempting.

Files:
- `SKILL.md` — full skill definition

Pre-merge review and polish are the crew plugin's `crew:review` and `crew:polish` skills.

## settings.json

Contains no secrets. Does contain:

- `model` — the default model (`opus[1m]`)
- `OBSIDIAN_VAULT` — absolute path to the Obsidian vault on this machine
- `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` — enables the agent teams feature
- `permissions.deny` — blocks Claude from reading `.env*` files and `~/.ssh/**`
- `hooks` — SessionStart, PreCompact, and PostToolUse hooks (see Hooks section)
- `autoMemoryEnabled` / `autoDreamEnabled` — automatic memory and consolidation
- `spinnerVerbs` — a large set of Discworld-themed loading messages, because why not

The `OBSIDIAN_VAULT` path will need updating on any machine other than the original.

The Obsidian MCP Server configuration (including the API key) lives in `~/.claude.json` at user scope, not in this file — it is machine-specific and not tracked in git.

## Design Decisions

This section explains *why* the system is structured the way it is. The what is in the sections above. The why is what makes it transferable.

### Skills as the capability layer

Agents have domains. Skills give them specific procedural knowledge to act on those domains reliably.

An agent told to use TDD is following an instruction. An agent with the `test-driven-development` skill has documented practice to follow. The distinction matters under pressure — when the task is complex and the temptation is to skip the test and just ship, the skill is what holds the line.

Skills are installed globally so they travel across projects.

---

## The Transferable Pattern

The crew plugin is one implementation of a more general architecture. You do not need a theme. You do not need ten agents. You need the structure.

### The pattern

```
┌─────────────────────────────────────────┐
│           Lead Agent                    │
│  Receives requests, owns the session,   │
│  collects findings, presents output     │
└──────────────┬──────────────────────────┘
               │
               │ assigns with justification
    ┌──────────┼──────────┐
    │          │          │
┌───▼───┐ ┌───▼───┐ ┌────▼──┐
│ Spec- │ │ Spec- │ │ Spec- │
│ialist │ │ialist │ │ialist │
└───────┘ └───────┘ └───────┘
               │
    ┌──────────▼──────────┐
    │    Proof Artifacts  │
    │  (decisions, audit  │
    │   trail, context)   │
    └─────────────────────┘
```

### The five components

**1. A lead agent with a clear mandate**
One agent owns the session. It receives requests, decides what to do, collects output from specialists, and presents results. It does not do everything itself — it orchestrates.

The lead agent's personality (if it has one) should reflect the mandate: reluctant but thorough, confident and direct, whatever fits your working style. The key requirement is that it has a *consistent voice* so you always know what you're interacting with.

**2. A routing mechanism**
Something that maps requests to the right specialists without the lead agent having to make every routing decision. The simplest version is routing context loaded at session start that tells the lead which specialist fits which kind of work.

The routing mechanism should justify its assignments. One sentence per agent. If it can't justify an inclusion, the agent isn't needed.

**3. Specialists with constrained domains**
Each specialist owns one domain and only one domain. They have clear rules about what they will and won't do, what triggers an escalation, and — crucially — what their output format looks like.

Constrained domains produce predictable output. Predictable output is how you keep AI on track.

Consider which specialists should be read-only reviewers that can block a change. A block should be a clear verdict with a reason — no debates, no stalling.

**4. Skills as the capability layer**
Skills give specialists procedural knowledge to act on their domains reliably. A specialist that "knows about security" behaves differently from a specialist that has `security-best-practices` loaded — the skill provides documented practice to follow, not just an instruction to obey.

Install skills globally so they travel across projects. Define trigger conditions per agent so the lead agent knows when to lean on a capability, not just that it exists.

**5. A proof artifact mechanism**
Something that captures what happened, what was decided, and what was found — in a format that's readable out of context, weeks later, by someone who wasn't in the session.

This is the feedback loop that makes the system self-correcting over time. Without it, every session starts cold. With it, decisions compound.

### Adapting this for your own setup

A minimal version of this pattern is three files:

- `CLAUDE.md` — your lead agent persona, routing guidance, and governance rules
- `agents/reviewer.md` — a read-only specialist for the domain that causes you the most problems
- `agents/builder.md` — a specialist that writes, ideally in an isolated worktree

You don't need ten specialists. Start with the domains that cause the most problems in your current workflow. Add agents when you find yourself repeatedly routing a type of request that doesn't fit the existing specialists.

You don't need a theme. Your version can be named after anything, or nothing. What matters is that each agent has a *defined voice and explicit constraints*, not what you call it.
